# نشر err-guard والتراجع عنه (خطة، لم تُنفَّذ)

## قبل النشر
1. run-all على الفرع: كل المجموعات ناجحة، ومنها err وerr-workerd.
2. فحص الإعداد دون اتصال: `wrangler deploy --dry-run` يُظهر ERRGATE (Durable Object) وBAK وAI.
3. نسخة احتياطية متحقَّق منها، يأخذها المشرف من صفحة الحماية:
   «نسخة الآن» ← «تحقق كامل» يقول «مطابقة» ← «تنزيل» الملف إلى الهاتف ← فحص الملف دون اتصال (tests/backup-diff/inspect.sh).
4. تسجيل رقم النسخة الحالية للخادم من لوحة Cloudflare (Deployments)، ولقطة من صفحة الأخطاء وعدد وثائقها.

## النشر (بموافقة صريحة)
- دمج err-guard في main (تقديم مباشر). يشغّل «نشر الخادم» تلقائيًا، فيُنشأ الكائن الدائم ErrGate لأول مرة (ترحيل v1)،
  ويعيد GitHub Pages نشر الموقع (ملفات التطبيق لم تتغير). لا APK.

## التحقق بعد النشر (قراءة فقط)
1. سير «نشر الخادم» ناجح، وسجله يذكر env.ERRGATE (ErrGate) Durable Object.
2. المزامنة تعمل في تطبيق طفل (فتح التطبيق، مراجعة، ثم الملف).
3. صفحة الأخطاء تفتح، والأخطاء القديمة كما هي.
4. خلال 24 ساعة: لوحة Durable Objects (طلبات وصفوف قليلة)، وطلبات Worker اليومية، واستهلاك Firestore.
5. بعد الاستقرار: تحديث RELEASED في إيداع مستقل (tests/set-released.sh).

## التراجع
- لا يمكن الرجوع من لوحة Cloudflare إلى نسخة ما قبل النشر: ترحيل الكائن الدائم يمنع الرجوع إلى ما قبله.
- الأسرع، دون نشر شيفرة: متغيّر ERR_MODE=off في إعدادات الخادم في لوحة Cloudflare، فيتوقف تسجيل الأخطاء كله
  (لا بوّابة ولا Firestore)، وكل ما عداه يعمل. يُزال المتغيّر لإعادة التسجيل.
- تراجع بالشيفرة: إيداع جديد على main يعيد handleErr القديم مع إبقاء صنف ErrGate وترحيله كما هما (حذفهما يحتاج ترحيل حذف يمحو بيانات البوّابة).
  لكن handleErr القديم يعيد الثغرة، فالأفضل ERR_MODE=off ثم إصلاح.
- البيانات: هذا التغيير لا يلمس بيانات المستخدمين. وثائق الأخطاء الجديدة بصيغة القديمة نفسها (مع حقل san)، فيقرؤها الخادم القديم والصفحة.
  لا حاجة إلى استرجاع نسخة احتياطية بسبب هذا التغيير؛ النسخة احتياط عام فقط.
